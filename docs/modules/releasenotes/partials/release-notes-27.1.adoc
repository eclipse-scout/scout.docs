== Application-Scoped REST Resources

REST resources implementing `IRestResource` are now registered as application-scoped singletons and reused by Jersey/HK2 across requests instead of creating a new resource instance for every request.

This reduces object creation overhead and aligns the lifecycle of REST resources with other application-scoped Scout components. As resource instances are shared, REST resources should be implemented as stateless components.

[[batch-support]]
== Batch Support for Scout JS Columns

The support for batched value formatting for Columns has been improved.
Each subclass of `Column` can assign the new `_batchFormat` property to format values in a single batch call.
This improves performance on large tables.

For this a new `BatchCall` helper class has been added to collect the keys of the batch and perform the asynchronous calls.
Refer to the JsDoc of the class for details and a usage example.

The new batch support is used by default by the `SmartColumn` and the `LookupColumn`.
Furthermore, `StaticLookupCall` is now batched.

== Expanded Anti-CSRF Support

Anti-CSRF protection has been extended to Jetty-based applications.

While REST applications were already protected using `AntiCsrfContainerFilter`, Jetty applications can now use the new `AntiCsrfFilter`.
The filter is registered by default through `UiServletContributors` for the path `/*`.

Paths can be excluded from Anti-CSRF validation by providing an implementation of `IAntiCsrfFilterExclusion`.

Implementations of `IAntiCsrfFilterExclusion` are now managed as application-scoped singletons and reused across requests.

== Support for placeholders

Form fields can now be configured with placeholder text.
If supported by the field type, the configured text is displayed when the field is empty.

== Data Object Improvements (Scout JS)

=== More Supported Type Constructs

The build-time detection of the attribute data types of data objects now resolves many more TypeScript type constructs:

* Enums (string, numeric and mixed)
* Type aliases
* Literal types and unions of literals
* `typeof` constants, e.g. `typeof ID_TYPE_NAME`
* Enum-like objects, e.g. `EnumObjectLike<typeof Colors>`, including static class properties like `Permission.Level`
* Type parameters: the constraint or default type is used, e.g. for `LookupRowDo<TKey>`
* `readonly` arrays, `ReadonlyArray`, `ReadonlyMap` and `ReadonlySet`
* Utility types `Partial`, `Required`, `Readonly` and `NonNullable`
* Parenthesized types

Furthermore, the value of the `@typeName` decorator can now refer to a class constant, e.g. `@typeName(MyDo.TYPE_NAME)`.

=== Empty @typeName No Longer Required

All classes extending `BaseDoEntity` directly or indirectly are now detected automatically, even without a `@typeName` decorator.
Empty `@typeName()` decorators, e.g. on abstract data object classes, are therefore obsolete and can be removed.

=== New Convenience Functions

The `dataObjects` utility offers new functions to inspect a data object.
They ignore the internal properties `_type`, `_typeVersion` and `_contributions`:

* `dataObjects.isEmpty`
* `dataObjects.keys`
* `dataObjects.values`
* `dataObjects.entries`

The names of the internal properties are available as constants: `dataObjects._TYPE_ATTRIBUTE_NAME`, `dataObjects._TYPE_VERSION_ATTRIBUTE_NAME` and `dataObjects._CONTRIBUTIONS_ATTRIBUTE_NAME`.
`objects.isEmpty` delegates to `dataObjects.isEmpty` for `BaseDoEntity` instances.

=== Data Objects in ModelAdapters

A `ModelAdapter` can declare properties containing data objects using `_addDataObjectProperties`.
These properties are automatically deserialized when the model is initialized and on property change and model events, and serialized when sent to the UI server.

[source,typescript,opts=novalidate]
----
export class MyWidgetAdapter extends ModelAdapter {
  constructor() {
    super();
    this._addDataObjectProperties(['data']);
  }
}
----

The built-in adapters (`HybridManagerAdapter`, `JsFormAdapter`, `OutlineAdapter`, ...) use this mechanism as well.
Hybrid actions, JS forms and JS pages therefore now work with `BaseDoEntity` instances.

=== ValueDo Support

`ValueDo` is now a class extending `BaseDoEntity` and is (de)serialized by the new `ValueDoSerializer`, e.g. the `value` of a `scout.DateValue` is converted to a `Date`.
Instances are created using factory methods:

[source,typescript,opts=novalidate]
----
let name = ValueDo.ofString('Scout');
let date = ValueDo.ofDate(new Date());
let custom = ValueDo.of('my.CustomValue', 'abc');
----

The type names of the built-in value types are available as constants: `ValueDo.STRING`, `ValueDo.LONG`, `ValueDo.BOOLEAN`, `ValueDo.DATE`, `ValueDo.DATE_TIME`, ...
Custom value types are registered using `ValueDoSerializer.get().addTypeName()`.

=== More Data Objects Migrated to Classes

The remaining built-in data objects have been migrated to classes extending `BaseDoEntity`: `ErrorDo`, `CalendarResourceDo`, `LookupRowDo`, `LookupResponse`, `LimitedResultInfoContributionDo` and `ValueDo`.
The new `AbstractLookupRestrictionDo` allows to create typed lookup restrictions for the `RestLookupCall`.

=== Further Improvements

* The `_typeVersion` attribute is retained by default when deserializing, so a data object can be sent back to the Java backend unchanged.
* `BaseDoEntity.equals` ignores `_typeVersion` if only present in one of the objects and treats `undefined` properties like missing properties.
* The new deserializer option `deserializeBaseDoEntity` controls whether attributes which are already data objects are deep copied (default) or shared.
* The new serializer option `retainTypeVersion` controls whether the `_typeVersion` attribute is written when serializing, like the option of the same name for deserializing.
It is passed to `dataObjects.serialize` and `dataObjects.stringify` and accepts a boolean or a predicate (default `true`).
Use it to compare data objects by their serialized form consistently with `BaseDoEntity.equals`, e.g. as `Map` keys:
+
[source,typescript,opts=novalidate]
----
let key = dataObjects.stringify(myDo, {retainTypeVersion: false});
----

For the necessary migration steps, see the xref:migration:migration-guide.adoc#dataobject-improvements-for-typescript[Migration Guide].

== DoMapEntity Instead of Map in REST Resources

REST resources must not return a `Map` directly; return a `DoMapEntity` instead.
`AbstractRestResourceAnnotationTest` now verifies this for all REST resources.
The new factory methods `DoMapEntity.of(Map)` and `DoMapEntity.create()` as well as `putAll(Map)` simplify the conversion.

== Switch to Native Promises (Scout JS)

We migrated the whole codebase of Scout JS from jQuery promises to native promises.

This gives the following advantages:

* *Modern language integration*: `async/await` can be used everywhere, as well as built-in features like `Promise.all()`, `Promise.race()`, `Promise.allSettled()` and `Promise.any()`.
* *Improved readability*: No conversion between jQuery and native promises is necessary anymore.
The type is more compact (`Promise` instead of `JQuery.Promise`), and the pattern is consistent throughout the codebase (no `done/fail/always`).
* *Better interoperability*: Native promises work seamlessly with modern JavaScript APIs (like `fetch`) and third-party libraries.
* *Simpler error handling*: Rejections propagate consistently through promise chains and unhandled rejections are handled globally.
Rejections always carry a single reason, e.g. an `AjaxError`, instead of an argument list.
* *Improved efficiency*: Native promises use the microtask queue instead of timer-based scheduling, reducing scheduling overhead and allowing asynchronous operations to complete sooner.
Promise chains also execute before the next rendering opportunity, potentially reducing unnecessary intermediate UI updates.
* *Standard JavaScript API*: Eliminates the dependency on jQuery for asynchronous operations.

To migrate existing code, see the xref:migration:migration-guide.adoc#native-promises[Migration Guide].

== Improved Error Handling (Scout JS)

* Unhandled rejections are now passed to the `ErrorHandler`, like uncaught errors in synchronous code.
You no longer need to add `App.get().errorHandler.handle(error)` to report errors.
`Form.load()`, `save()` and `validate()` no longer show a message box themselves, they reject and leave the error to the global handler.
* Every error is reported only once: the `ErrorHandler` marks handled errors as consumed and ignores them afterward.
To show a custom message instead of the default one, call `ErrorHandler.consume(error)` and rethrow the error.
* `ErrorHandler.handle()` has been simplified and now has only one argument.
* If the error has a `cause` it is now logged by the `ErrorHandler`.
* Abort handling has been improved:
** The `AbortError` is ignored by the `ErrorHandler` and doesn't need to be caught.
** The global rejection handler also ignores rejections without a reason.
** Ajax calls now throw `AbortError` instead of `AjaxError` with status `aborted`.
** `ErrorHandler.handleOrAbort()` rejects with an `AbortError` instead, to skip the following `.then()` steps of an aborted chain.
** `Widget.throwAbortIfDestroyed()` throws an `AbortError` if the widget is destroyed or being destroyed.
Use it in asynchronous code to stop a promise chain before accessing a widget that has been destroyed in the meantime, e.g. when a form is closed while a request is running.


For details, see xref:technical-guide:user-interface/error-handling.adoc[Error Handling].

Scout now uses TypeScript 6.0 (see https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html[TypeScript 6.0 release notes]).

[[ecmascript-2023]]
== ECMAScript 2023 (Scout JS)

The full ECMAScript 2023 feature set can now be used, e.g. `Array.prototype.findLast()`, `toSorted()`, `toReversed()`, `toSpliced()` and `with()`.
The `lib` of `@eclipse-scout/tsconfig` has been raised from `ES2022` to `ES2023`.

The minimum supported browser versions have been raised accordingly:

* Mozilla Firefox >= 146
* Chromium (like Google Chrome, Microsoft Edge, Brave or Opera) >= 110
* Apple Safari >= 16.4 (iOS >= 16.4)

As all supported browsers natively support ES2023, Babel has been removed from the build:

* The `target` of `@eclipse-scout/tsconfig` has been changed from `ESNext` to `ES2023`, so TypeScript compiles newer syntax down to ES2023.
* JavaScript files are no longer transpiled so developers still using JavaScript are encouraged to switch to TypeScript now. Otherwise, they have to ensure browser compatibility themselves.
Webpack configurations which reference `babel-loader` (e.g. to adjust its rules) need to be adjusted.

For details, see xref:technical-guide:user-interface/browser-support.adoc[Browser Support].

[[webpack-build]]
== Updated Webpack Build (Scout JS)

The webpack build of `@eclipse-scout/cli` has been updated to webpack 5.113 and now uses its built-in features instead of plugins which have been deprecated by the webpack team:

* CSS: The CSS compiled by `less-loader` is processed and extracted by webpack itself (https://webpack.js.org/guides/native-css/[native CSS]).
`css-loader` and `mini-css-extract-plugin` are no longer used.
* Static resources: The resources are copied by the `CopyPlugin` built into webpack instead of `copy-webpack-plugin`.
* Minification: JavaScript and CSS are minified by `minimizer-webpack-plugin` (using esbuild, as before) instead of `terser-webpack-plugin` and `css-minimizer-webpack-plugin`.

The output of the build is unchanged.
Furthermore, `fork-ts-checker-notifier-webpack-plugin` has been removed, so no desktop notification is shown anymore if the type check fails in watch mode.
The errors are still printed to the console.

To migrate custom webpack configurations, see the xref:migration:migration-guide.adoc#webpack-build[Migration Guide].
