== About This Document

This document describes all relevant changes *from Eclipse Scout {scout-previous-version} to Eclipse Scout {scout-version}*. If existing code has to be migrated, instructions are provided here.

== Obtaining the Latest Version

=== Scout Runtime for Java

Scout Runtime artifacts for Java are distributed using Maven Central:

* {maven-central-link} on _Maven Central_
* {mvnrepository-link} on _mvnrepository.com_

Usage example in the parent POM of your Scout application:

[source,xml]
[subs="verbatim,attributes"]
----
<dependency>
    <groupId>org.eclipse.scout.rt</groupId>
    <artifactId>org.eclipse.scout.rt</artifactId>
    <version>{maven-version}</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>
----

* https://www.npmjs.com/package/@eclipse-scout/core[Scout Core Runtime]

== New Build & Runtime Requirements

Scout 27.1 requires at least the following:

* Build and runtime of Scout 27.1 require Java 25. The compiler target level is set to Java 21.
* Furthermore, the build requires
** Node: >= 24.12.0
** Pnpm: >= 10.26.1

== Batch Support for Scout JS Columns

The batch support for `Columns` has been improved (see the xref:release-notes.adoc#batch-support[release notes] for details).

The signature for the following functions changed:

* `Column.formatValue`, `Column.formatter` and `Column._formatValue`: Now returns `string | JQuery.Promise<BatchCallResult<TValue, unknown>>` returning all key-value-mappings in the batched async case.
* `Column.setCellTextDeferred` now expects this `JQuery.Promise<BatchCallResult<TValue, unknown>>` as argument for the async case. The `row` and `cell` arguments have been deleted as such a call is no longer executed for each row, but once for all rows.
+
To access or modify the new value by cell or row use `_batchFormatResultToCellText` which will be called for each row in the batch result.

The `StaticLookupCall` and `LookupColumn` now have batching enabled by default.
This means all `StaticLookupCalls` and all `LookupColumns` using a batch-enabled `LookupCall` (like `StaticLookupCall` now) do no longer get the `row` argument in the `prepareLookupCall` event (as they are batched now for several rows).
So, if you use the `row` property in a `prepareLookupCall` event listener, you have to do one of the following:

* If possible: Change the listener implementation so that the row is no longer required.
* Set the `batch` property of the `LookupCall` to `false`. Then the old behavior without batching is applied in which the row is passed to the listener again. Please note that this is not recommended for large tables as it is much slower!

== Move ResultInfo from PageWithTable to Table

In Scout Classic the following methods have been moved:

* `IPageWithTable.setResultInfo` -> `ITable.setResultInfo`
* `AbstractPageWithTable.isLimitedResult` -> `ITable.isLimitedResult`
* `AbstractPageWithTable.setLimitedResult` -> `ITable.setLimitedResult`

So intead calling these methods on the page, call them on the corresponding Table. E.g. `myPage.getTable().setResultInfo()`.

In Scout JS the function `Table.setLimitedResultTableStatus` was renamed to `Table.updateLimitedResultTableStatus` and requires no argument anymore as the table now directly holds the `limitedResult` property. Furthermore, the function `TableMaxResultsHelper.isLoadMoreDataPossible` now requires the whole table as argument for maximum flexiblity.

== Moved classes for Expanded Anti-CSRF Support

The following classes have been moved from the REST module to the security module:

* `org.eclipse.scout.rt.rest.csrf.AntiCsrfHelper` → `org.eclipse.scout.rt.security.csrf.AntiCsrfHelper`
* `org.eclipse.scout.rt.rest.csrf.IAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.IAntiCsrfFilterExclusion`
* `org.eclipse.scout.rt.rest.csrf.HttpMethodAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.HttpMethodAntiCsrfFilterExclusion`

== Changed Method Signature for ITileDataLoader#loadData

The method signature of `org.eclipse.scout.rt.client.ui.tile.AbstractTile.ITileDataLoader.loadData` changed from `loadData()` to `loadData(boolean autoReloadMode)`.
The new Parameter `autoReloadMode` specifies if the load of the Tile shall be done in an automatic reload mode.
That means the loading indicator will not be shown.

To get the same behavior as before, set the parameter to `false`.

== API Changes regarding Table Tiles

The following method signatures have changed:

* `ITable.createTiles`
** old: `List<ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
** new: `List<? extends ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
* `ITableTileGridMediator.getTileMappings`
** old: `List<ITableRowTileMapping> getTileMappings()`
** new: `List<? extends ITableRowTileMapping> getTileMappings()`
* `ITableTileGridMediator.setTileMappings`
** old: `void setTileMappings(List<ITableRowTileMapping> tileMappings)`
** new: `void setTileMappings(List<? extends ITableRowTileMapping> tileMappings)`
* `ITableRowTileMapping.withTableRow`
** old: `TableRowTileMapping withTableRow(ITableRow tableRow)`
** new: `ITableRowTileMapping withTableRow(ITableRow tableRow)`
* `ITableRowTileMapping.withTile`
** old: `TableRowTileMapping withTile(ITile tile)`
** new: `ITableRowTileMapping withTile(ITile tile)`

All implementations and usages may need to be adjusted.

== Support for placeholders

Placeholder support has been added at top level and is therefore available throughout the form field hierarchy.
As a consequence, this change may affect existing customizations in your project.

Scout Classic

- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.getPlaceholder()`
- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.setPlaceholder(String)`
- `org.eclipse.scout.rt.client.ui.form.fields.AbstractFormField.getConfiguredPlaceholder()`

Scout JS

- `FormField.placeholder`
- `FormField.setPlaceholder(string)`

Please review your project for potential conflicts:

- If you have implemented custom placeholder functionality, consider removing or migrating those customizations to the new built-in API.
- If you have introduced custom methods named `getPlaceholder()`, `setPlaceholder()`, or similar on form fields, consider renaming them to avoid naming conflicts and unintended behavior.


== DataObject Improvements for TypeScript

=== TypeVersion Attribute

When deserializing a dataobject, the `_typeVersion` attribute is now always retained by default.
In former releases the default was to only retain it if the target object is not a `BaseDoEntity`.
This change makes it more consistent and ensures the dataobject can be sent back to the Java backend without difference.

It might require some adaptations in your code in rare cases if you rely on the absence of this property.
Either migrate your code or explicitly set the `retainTypeVersion` property of the deserializer to `false`.

=== Equality Behavior when Comparing DataObjects

The `equals` function of `BaseDoEntity` ignores the `_typeVersion` property if only existing in one of the compared objects.
This ensures a deserialized object from the Java server is equal to an object directly created in TypeScript using `scout.create` when having the same attributes.

Furthermore, a property having the value `undefined` is considered to be equal to not having the property at all.
This makes the `equals` function less strict but better aligns with the usually expected behavior.

=== RestLookupCall Uses BaseDoEntity

The `RestLookupCall` has been migrated to use `BaseDoEntity`. Therefore, `restriction` can now also be a `BaseDoEntity` including automatic serialization and the `LookupRowDo` included in the response is a `BaseDoEntity` as well instead of plain JavaScript POJOs.

This allows you to create specific `LookupRowDo` or `AbstractLookupRestrictionDo` classes if required.
The corresponding functions `_acceptLookupRow` and `_createLookupRowFromDo` can then directly use your named classes if the `_type` attribute included in the response matches the one declared in your TS class.

=== Other Data Objects Migrated from Interfaces to Classes

The following data objects have been migrated from interfaces extending `DoEntity` to classes extending `BaseDoEntity`:

[cols="1,1"]
|===
|Class |Type Name

|`ErrorDo` |`scout.Error`
|`CalendarResourceDo` |`scout.CalendarResource`
|`LookupRowDo` |none (base class for lookup rows)
|`LookupResponse` |`scout.LookupResponse`
|`LimitedResultInfoContributionDo` |`scout.LimitedResultInfoContribution`
|`ValueDo` |set per instance (see below)
|`AbstractLookupRestrictionDo` (new) |none (abstract base for lookup restrictions)
|===

Migration:

* Replace object literals typed with one of these types by instances: `scout.create(CalendarResourceDo, {resourceId: ..., visible: true})`.
* Replace `interface MyLookupRowDo extends LookupRowDo<string>` by `@typeName('my.LookupRow') class MyLookupRowDo extends LookupRowDo<string>`. The type name must match the `@TypeName` of the Java class.
* The type parameter of `LookupResponse` must now extend `LookupRowDo`.
* `AjaxError.errorDo` is now always an `ErrorDo` instance. `AjaxError.isErrorDo` is now a type guard for `ModelOf<ErrorDo>`.
* `Calendar.setResources` and `CalendarModel.resources` accept models as well. Use `CalendarResourceDo.ensure` to convert a model to an instance.
* `LimitedResultInfoContributionDo.TYPE_NAME` holds the type name.

=== ValueDo

`ValueDo` is now a class. Its `_type` (e.g. `scout.StringValue`) is set per instance and is available as constants (`ValueDo.STRING`, `ValueDo.LONG`, `ValueDo.DATE`, ...).
Create instances using the factory methods `ValueDo.ofString`, `ofLong`, `ofBoolean`, `ofDate`, `ofDateTime` or `ValueDo.of(typeName, value)` instead of object literals.

Value data objects are (de)serialized by the new `ValueDoSerializer`, e.g. the `value` of a `scout.DateValue` is converted to a `Date`.
Value types of your own project must be registered: `ValueDoSerializer.get().addTypeName('my.CustomValue', doValueMetaData.createSimple(String))`.
`ValueDoSerializer` always creates `ValueDo` instances, subclasses of `ValueDo` are not supported.

=== Removed and Renamed APIs

[cols="1,1"]
|===
|Old |New

|`AnyDoEntity` |`BaseDoEntity` (or `DoEntity` for plain objects)
|`CodeDo.text` |Removed. Use `texts`.
|`DataObjectDeserializer._TYPE_VERSION_ATTRIBUTE_NAME` |`dataObjects._TYPE_VERSION_ATTRIBUTE_NAME`
|`doValueMetaData.getArrayValueType` |`doValueMetaData.getFirstTypeArg`
|===

New constants: `dataObjects._TYPE_ATTRIBUTE_NAME` and `dataObjects._CONTRIBUTIONS_ATTRIBUTE_NAME`.

New utility functions: `dataObjects.isEmpty`, `dataObjects.keys`, `dataObjects.values` and `dataObjects.entries`.
They ignore `_type`, `_typeVersion` and `_contributions`.
`objects.isEmpty` delegates to `dataObjects.isEmpty` for `BaseDoEntity` instances. A `BaseDoEntity` is therefore empty if all its properties except the ones mentioned above are `undefined`.

=== HybridManager Requires BaseDoEntity

The `data` parameter of `HybridManager.callAction`, `callActionAndWait`, `callActionAndWaitWithContext`, `openForm` and `createForm` is now of type `BaseDoEntity`.
The `data` of `HybridActionEvent` and `HybridActionEndEvent` and the result of `callActionAndWait` are `BaseDoEntity` instances as well.

Migration: replace object literals by data object classes with a `@typeName` matching the Java data object.
The data is serialized using `dataObjects.serialize`.

=== Unknown Data Objects

The following data is now deserialized without the `createPojoIfDoIsUnknown` option:

* data of hybrid actions and hybrid widget events (`HybridManagerAdapter`)
* `inputData` and `jsFormModel` of JS forms (`JsFormAdapter`)
* `jsPageModel` of JS pages (`OutlineAdapter`)

Objects whose `_type` cannot be resolved to a class and objects not having `_type` are now deserialized to plain `BaseDoEntity` instances instead of plain JavaScript objects.

Migration:

* Declare a class with a matching `@typeName` for each data object you access.
* Use `dataObjects.stringify` instead of `JSON.stringify`.
* Do not compare such objects to object literals as `objects.equals` and `objects.equalsRecursive` consider objects with different prototypes as not equal.

=== Data Object Visitors

`dataObjectVisitors` now visits all properties of a `BaseDoEntity` except `_type`, `_typeVersion` and `_contributions`. Before, all properties starting with `_` were skipped.

=== Data Object Properties in ModelAdapter

A `ModelAdapter` can now declare properties containing data objects using `_addDataObjectProperties`.
These properties are deserialized when the model is initialized, on property change and model events, and serialized when sent to the server.
Replace manual calls to `dataObjects.deserialize` and `dataObjects.serialize` in your adapters by this declaration.

`ModelAdapter._remoteProperties` is now a `Set` instead of an array. `_addProperties` and `_removeProperties` only support `Set` containers.

== REST Resources Must Not Return Maps

`AbstractRestResourceAnnotationTest` contains the new test `testMapReturnValue`, which fails for REST resource methods returning a `java.util.Map`.
Return a `DoMapEntity` instead. It can be created from a map using `DoMapEntity.of(map)` (keys must be converted to Strings first).

Override `acceptResourceForMapReturnValueCheck` or `acceptMethodForMapReturnValueCheck` to exclude resources or methods from the check.
