== About This Document

This document describes all relevant changes *from Eclipse Scout {scout-previous-version} to Eclipse Scout {scout-version}*. If existing code has to be migrated, instructions are provided here.

== Obtaining the Latest Version

=== Scout Runtime for Java

Scout Runtime artifacts for Java are distributed using Maven Central:

* {maven-central-link} on _Maven Central_
* {mvnrepository-link} on _mvnrepository.com_

Usage example in the parent POM of your Scout application:

[source,xml]
[subs="verbatim,attributes"]
----
<dependency>
    <groupId>org.eclipse.scout.rt</groupId>
    <artifactId>org.eclipse.scout.rt</artifactId>
    <version>{maven-version}</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>
----

== Batch Support for Scout JS Columns

The batch support for `Columns` has been improved (see the xref:releasenotes:release-notes.adoc#batch-support[release notes] for details).

The signature for the following functions changed:

* `Column.formatValue`, `Column.formatter` and `Column._formatValue`: Now returns `string | Promise<BatchCallResult<TValue, unknown>>` returning all key-value-mappings in the batched async case.
* `Column.setCellTextDeferred` now expects this `Promise<BatchCallResult<TValue, unknown>>` as argument for the async case. The `row` and `cell` arguments have been deleted as such a call is no longer executed for each row, but once for all rows.
+
To access or modify the new value by cell or row use `_batchFormatResultToCellText` which will be called for each row in the batch result.

The `StaticLookupCall` and `LookupColumn` now have batching enabled by default.
This means all `StaticLookupCalls` and all `LookupColumns` using a batch-enabled `LookupCall` (like `StaticLookupCall` now) do no longer get the `row` argument in the `prepareLookupCall` event (as they are batched now for several rows).
So, if you use the `row` property in a `prepareLookupCall` event listener, you have to do one of the following:

* If possible: Change the listener implementation so that the row is no longer required.
* Set the `batch` property of the `LookupCall` to `false`. Then the old behavior without batching is applied in which the row is passed to the listener again. Please note that this is not recommended for large tables as it is much slower!

== Move ResultInfo from PageWithTable to Table

In Scout Classic the following methods have been moved:

* `IPageWithTable.setResultInfo` -> `ITable.setResultInfo`
* `AbstractPageWithTable.isLimitedResult` -> `ITable.isLimitedResult`
* `AbstractPageWithTable.setLimitedResult` -> `ITable.setLimitedResult`

So intead calling these methods on the page, call them on the corresponding Table. E.g. `myPage.getTable().setResultInfo()`.

In Scout JS the function `Table.setLimitedResultTableStatus` was renamed to `Table.updateLimitedResultTableStatus` and requires no argument anymore as the table now directly holds the `limitedResult` property. Furthermore, the function `TableMaxResultsHelper.isLoadMoreDataPossible` now requires the whole table as argument for maximum flexiblity.

== Moved classes for Expanded Anti-CSRF Support

The following classes have been moved from the REST module to the security module:

* `org.eclipse.scout.rt.rest.csrf.AntiCsrfHelper` → `org.eclipse.scout.rt.security.csrf.AntiCsrfHelper`
* `org.eclipse.scout.rt.rest.csrf.IAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.IAntiCsrfFilterExclusion`
* `org.eclipse.scout.rt.rest.csrf.HttpMethodAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.HttpMethodAntiCsrfFilterExclusion`

== Changed Method Signature for ITileDataLoader#loadData

The method signature of `org.eclipse.scout.rt.client.ui.tile.AbstractTile.ITileDataLoader.loadData` changed from `loadData()` to `loadData(boolean autoReloadMode)`.
The new Parameter `autoReloadMode` specifies if the load of the Tile shall be done in an automatic reload mode.
That means the loading indicator will not be shown.

To get the same behavior as before, set the parameter to `false`.

== API Changes regarding Table Tiles

The following method signatures have changed:

* `ITable.createTiles`
** old: `List<ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
** new: `List<? extends ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
* `ITableTileGridMediator.getTileMappings`
** old: `List<ITableRowTileMapping> getTileMappings()`
** new: `List<? extends ITableRowTileMapping> getTileMappings()`
* `ITableTileGridMediator.setTileMappings`
** old: `void setTileMappings(List<ITableRowTileMapping> tileMappings)`
** new: `void setTileMappings(List<? extends ITableRowTileMapping> tileMappings)`
* `ITableRowTileMapping.withTableRow`
** old: `TableRowTileMapping withTableRow(ITableRow tableRow)`
** new: `ITableRowTileMapping withTableRow(ITableRow tableRow)`
* `ITableRowTileMapping.withTile`
** old: `TableRowTileMapping withTile(ITile tile)`
** new: `ITableRowTileMapping withTile(ITile tile)`

All implementations and usages may need to be adjusted.

== Support for placeholders

Placeholder support has been added at top level and is therefore available throughout the form field hierarchy.
As a consequence, this change may affect existing customizations in your project.

Scout Classic

- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.getPlaceholder()`
- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.setPlaceholder(String)`
- `org.eclipse.scout.rt.client.ui.form.fields.AbstractFormField.getConfiguredPlaceholder()`

Scout JS

- `FormField.placeholder`
- `FormField.setPlaceholder(string)`

Please review your project for potential conflicts:

- If you have implemented custom placeholder functionality, consider removing or migrating those customizations to the new built-in API.
- If you have introduced custom methods named `getPlaceholder()`, `setPlaceholder()`, or similar on form fields, consider renaming them to avoid naming conflicts and unintended behavior.

== Changes in scout#cloneShallow

The signature of `scout.cloneShallow` has changed:

* old: `cloneShallow(template: object, properties?: object, createUniqueId?: boolean): object`
* new: `cloneShallow<T extends object>(template: T, properties?: object, createUniqueId = true): T`

With this, casting the result is no longer necessary. Code like

[source,typescript,opts=novalidate]
.Old
----
class Foo {
  clone(properties?: object): Foo {
    return scout.cloneShallow(this, properties, true) as Foo;
  }
}
----

can be migrated to

[source,typescript,opts=novalidate]
.New
----
class Foo {
  clone(properties?: object): Foo {
    return scout.cloneShallow(this, properties);
  }
}
----

The default value of the parameter `createUniqueId` is still `true` but its handling was slightly changed.
Explicitly using the value `null` or `undefined` was handled the same way as not using the parameter at all resulting in a unique id being created.
Now `false` or any falsy value including `null` (but not `undefined`) that is passed to the function is interpreted as `false` while `true`, any truthy value, `undefined` or not passing the value is interpreted as `true`.

== jquery-scout: oneAnimationEnd Changed

`oneAnimationEnd` has been improved so the callback is now executed even when debugging or if the `animation-duration` is set to 0s.

This also comes with a behavior change: the function now must be called after the animation has been started, e.g. after a class that starts the animation has been added.
If `oneAnimationEnd` is called before adding the animation class, the callback won't be executed anymore.

== jQuery Promises Replaced by Native Promises (Scout JS)

Scout JS no longer uses jQuery `Deferred`/`Promise`.
Every API that returned a `JQuery.Promise<T>` now returns a native `Promise<T>`, the Scout `Deferred` class is based on native promises, and `.done()`, `.fail()` and `.always()` are no longer available on the returned promises.
Project code that overrides or calls these APIs, including specs, has to be migrated.

=== Most Important Changes

* *Types*: replace `+JQuery.Promise<T>+` with `Promise<T>` and `+$.Deferred()+` with `+new Deferred<T>()+` of `@eclipse-scout/core`.
The TypeScript compiler reports almost all places that need a change.
* *Semantics*: `.done()`, `.fail()` and `.always()` can't be replaced one-to-one by `.then()`, `.catch()` and `.finally()`.
All `.done()` handlers receive the original value, `.finally()` receives no value, a `.catch()` without rethrow resolves the chain, and native promises resolve and reject with exactly one value (e.g. `$.promiseAll()` and `$.when()` callbacks receive one array).
Review each of these places individually.
* *Timing*: native promises continue as microtasks, jQuery `.then()` handlers ran in a `setTimeout`.
`jasmine.clock().tick()` no longer drives promise chains: specs have to await the returned promise or an event (`+widget.when(...)+`) instead.
Asynchronous work started while opening a form without awaiting its promise (e.g. a lookup in `Form.importData()`) is now overtaken the form itself and may lead to a wrong `saveNeeded` state. Try to return the promise, e.g. in `Form.importData()` which may now return a promise.
* *Errors*: unhandled rejections are no longer silently ignored.
A global handler passes them to the `ErrorHandler`, which logs them and shows the error message box, and specs fail on them.
Expected cancellations (`AbortError`, aborted ajax and lookup calls, rejections without a reason) are ignored.
Local `+.catch(error => errorHandler.handle(error))+` at the end of a promise chain are obsolete and can be removed. `ErrorHandler.handle()` does not accept multiple arguments anymore.
* *Forms*: `Form.load()`, `save()`, `ok()` and `validate()` no longer show the error message box themselves, they only reject.
`Form.close()` no longer returns a promise.

=== Recommended Approach: Migrate with an AI Agent

The migration consists of many small changes that are not purely mechanical.
We therefore recommend migrating with an AI coding agent like https://claude.com/claude-code[Claude Code] and reviewing the result.

Use the xref:promise-migration-guide.adoc[] as prompt for the agent.
It is written as instructions for an agent and contains the complete list of changed APIs, the translation rules and the pitfalls found in the migration of Scout and other projects.

After the migration review and test the changes thoroughly.
