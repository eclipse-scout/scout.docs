== About This Document

This document describes all relevant changes *from Eclipse Scout {scout-previous-version} to Eclipse Scout {scout-version}*. If existing code has to be migrated, instructions are provided here.

== New Build & Runtime Requirements

Scout 27.1 requires at least the following:

* Build and runtime of Scout 27.1 require Java 25. The compiler target level is set to Java 21.
* Furthermore, the build requires
** Node: >= 26.13.1
** Pnpm: >= 12.21.0

== Jackson Behavior Changes

When serializing an object without serializable properties, `IDataObjectMapper.writeValue` now returns an empty JSON object (`{}`) instead of throwing a `PlatformException`.

The default maximum nesting depth for JSON reading and writing has changed from 1000 to 500. Documents or data objects nested deeper than this limit may now fail to deserialize or serialize. To change the limits, configure the `maxNestingDepth` entry in the `scout.dataobject.jackson.streamReadConstraints` and/or `scout.dataobject.jackson.streamWriteConstraints` config properties.

The `IDataObjectSerializerProvider` API has changed signatures and new hooks, including `findCollectionLike*` and `findEnumSerializer`. Handling of `DoList`, `DoSet` and `DoCollection` has moved from `findSerializer` and `findDeserializer` to the collection-like hooks. Custom providers that override these methods must be updated to the new API.

== Batch Support for Scout JS Columns

The batch support for `Columns` has been improved (see the xref:releasenotes:release-notes.adoc#batch-support[release notes] for details).

The signature for the following functions changed:

* `Column.formatValue`, `Column.formatter` and `Column._formatValue`: Now returns `string | Promise<BatchCallResult<TValue, unknown>>` returning all key-value-mappings in the batched async case.
* `Column.setCellTextDeferred` now expects this `Promise<BatchCallResult<TValue, unknown>>` as argument for the async case. The `row` and `cell` arguments have been deleted as such a call is no longer executed for each row, but once for all rows.
+
To access or modify the new value by cell or row use `_batchFormatResultToCellText` which will be called for each row in the batch result.

The `StaticLookupCall` and `LookupColumn` now have batching enabled by default.
This means all `StaticLookupCalls` and all `LookupColumns` using a batch-enabled `LookupCall` (like `StaticLookupCall` now) do no longer get the `row` argument in the `prepareLookupCall` event (as they are batched now for several rows).
So, if you use the `row` property in a `prepareLookupCall` event listener, you have to do one of the following:

* If possible: Change the listener implementation so that the row is no longer required.
* Set the `batch` property of the `LookupCall` to `false`. Then the old behavior without batching is applied in which the row is passed to the listener again. Please note that this is not recommended for large tables as it is much slower!

== Move ResultInfo from PageWithTable to Table

In Scout Classic the following methods have been moved:

* `IPageWithTable.setResultInfo` -> `ITable.setResultInfo`
* `AbstractPageWithTable.isLimitedResult` -> `ITable.isLimitedResult`
* `AbstractPageWithTable.setLimitedResult` -> `ITable.setLimitedResult`

So intead calling these methods on the page, call them on the corresponding Table. E.g. `myPage.getTable().setResultInfo()`.

In Scout JS the function `Table.setLimitedResultTableStatus` was renamed to `Table.updateLimitedResultTableStatus` and requires no argument anymore as the table now directly holds the `limitedResult` property. Furthermore, the function `TableMaxResultsHelper.isLoadMoreDataPossible` now requires the whole table as argument for maximum flexiblity.

== Moved classes for Expanded Anti-CSRF Support

The following classes have been moved from the REST module to the security module:

* `org.eclipse.scout.rt.rest.csrf.AntiCsrfHelper` → `org.eclipse.scout.rt.security.csrf.AntiCsrfHelper`
* `org.eclipse.scout.rt.rest.csrf.IAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.IAntiCsrfFilterExclusion`
* `org.eclipse.scout.rt.rest.csrf.HttpMethodAntiCsrfFilterExclusion` → `org.eclipse.scout.rt.security.csrf.HttpMethodAntiCsrfFilterExclusion`

== Changed Method Signature for ITileDataLoader#loadData

The method signature of `org.eclipse.scout.rt.client.ui.tile.AbstractTile.ITileDataLoader.loadData` changed from `loadData()` to `loadData(boolean autoReloadMode)`.
The new Parameter `autoReloadMode` specifies if the load of the Tile shall be done in an automatic reload mode.
That means the loading indicator will not be shown.

To get the same behavior as before, set the parameter to `false`.

== API Changes regarding Table Tiles

The following method signatures have changed:

* `ITable.createTiles`
** old: `List<ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
** new: `List<? extends ITableRowTileMapping> createTiles(List<? extends ITableRow> rows)`
* `ITableTileGridMediator.getTileMappings`
** old: `List<ITableRowTileMapping> getTileMappings()`
** new: `List<? extends ITableRowTileMapping> getTileMappings()`
* `ITableTileGridMediator.setTileMappings`
** old: `void setTileMappings(List<ITableRowTileMapping> tileMappings)`
** new: `void setTileMappings(List<? extends ITableRowTileMapping> tileMappings)`
* `ITableRowTileMapping.withTableRow`
** old: `TableRowTileMapping withTableRow(ITableRow tableRow)`
** new: `ITableRowTileMapping withTableRow(ITableRow tableRow)`
* `ITableRowTileMapping.withTile`
** old: `TableRowTileMapping withTile(ITile tile)`
** new: `ITableRowTileMapping withTile(ITile tile)`

All implementations and usages may need to be adjusted.

== Support for placeholders

Placeholder support has been added at top level and is therefore available throughout the form field hierarchy.
As a consequence, this change may affect existing customizations in your project.

Scout Classic

- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.getPlaceholder()`
- `org.eclipse.scout.rt.client.ui.form.fields.IFormField.setPlaceholder(String)`
- `org.eclipse.scout.rt.client.ui.form.fields.AbstractFormField.getConfiguredPlaceholder()`

Scout JS

- `FormField.placeholder`
- `FormField.setPlaceholder(string)`

Please review your project for potential conflicts:

- If you have implemented custom placeholder functionality, consider removing or migrating those customizations to the new built-in API.
- If you have introduced custom methods named `getPlaceholder()`, `setPlaceholder()`, or similar on form fields, consider renaming them to avoid naming conflicts and unintended behavior.

== Changes in scout#cloneShallow

The signature of `scout.cloneShallow` has changed:

* old: `cloneShallow(template: object, properties?: object, createUniqueId?: boolean): object`
* new: `cloneShallow<T extends object>(template: T, properties?: object, createUniqueId = true): T`

With this, casting the result is no longer necessary. Code like

[source,typescript,opts=novalidate]
.Old
----
class Foo {
  clone(properties?: object): Foo {
    return scout.cloneShallow(this, properties, true) as Foo;
  }
}
----

can be migrated to

[source,typescript,opts=novalidate]
.New
----
class Foo {
  clone(properties?: object): Foo {
    return scout.cloneShallow(this, properties);
  }
}
----

The default value of the parameter `createUniqueId` is still `true` but its handling was slightly changed.
Explicitly using the value `null` or `undefined` was handled the same way as not using the parameter at all resulting in a unique id being created.
Now `false` or any falsy value including `null` (but not `undefined`) that is passed to the function is interpreted as `false` while `true`, any truthy value, `undefined` or not passing the value is interpreted as `true`.

[#dataobject-improvements-for-typescript]
== DataObject Improvements for TypeScript

=== TypeVersion Attribute

When deserializing a dataobject, the `_typeVersion` attribute is now always retained by default.
In former releases the default was to only retain it if the target object is not a `BaseDoEntity`.
This change makes it more consistent and ensures the dataobject can be sent back to the Java backend without difference.

It might require some adaptations in your code in rare cases if you rely on the absence of this property.
Either migrate your code or explicitly set the `retainTypeVersion` property of the deserializer to `false`.

=== Equality Behavior when Comparing DataObjects

The `equals` function of `BaseDoEntity` ignores the `_typeVersion` property if only existing in one of the compared objects.
This ensures a deserialized object from the Java server is equal to an object directly created in TypeScript using `scout.create` when having the same attributes.

Furthermore, a property having the value `undefined` is considered to be equal to not having the property at all.
This makes the `equals` function less strict but better aligns with the usually expected behavior.

Code comparing data objects by their serialized form (e.g. `dataObjects.stringify` results used as `Map` keys or signatures) does not apply these rules and may treat a data object received from the Java server as different from the same data object created in TypeScript.
Migration: pass the new serializer option `retainTypeVersion: false` to skip the `_typeVersion`, e.g. `dataObjects.stringify(myDo, {retainTypeVersion: false})`, or compare the data objects using `equals`.

=== RestLookupCall Uses BaseDoEntity

The `RestLookupCall` has been migrated to use `BaseDoEntity`.

This means that `LookupRowDos` having data objects as keys now deserialize to BaseDoEntity classes instead of POJOs.
Furthermore, `restriction` can now also be a `BaseDoEntity` including automatic serialization.
This allows you to create specific `LookupRowDo` or `AbstractLookupRestrictionDo` classes if required.
The corresponding functions `_acceptLookupRow` and `_createLookupRowFromDo` can then directly use your named classes if the `_type` attribute included in the response matches the one declared in your TS class.

=== Other Data Objects Migrated from Interfaces to Classes

The following data objects have been migrated from interfaces extending `DoEntity` to classes extending `BaseDoEntity`:

[cols="1,1"]
|===
|Class |Type Name

|`ErrorDo` |`scout.Error`
|`CalendarResourceDo` |`scout.CalendarResource`
|`LookupRowDo` |none (base class for lookup rows)
|`LookupResponse` |`scout.LookupResponse`
|`LimitedResultInfoContributionDo` |`scout.LimitedResultInfoContribution`
|`ValueDo` |set per instance (see below)
|`AbstractLookupRestrictionDo` (new) |none (abstract base for lookup restrictions)
|===

Migration:

* Replace object literals typed with one of these types by instances: `scout.create(CalendarResourceDo, {resourceId: ..., visible: true})`.
* Replace `interface MyLookupRowDo extends LookupRowDo<string>` by `@typeName('my.LookupRow') class MyLookupRowDo extends LookupRowDo<string>`. The type name must match the `@TypeName` of the Java class.
* The type parameter of `LookupResponse` must now extend `LookupRowDo`.
* `AjaxError.errorDo` is now always an `ErrorDo` instance. `AjaxError.isErrorDo` is now a type guard for `ModelOf<ErrorDo>`.
* `Calendar.setResources` and `CalendarModel.resources` accept models as well. Use `CalendarResourceDo.ensure` to convert a model to an instance.

=== ValueDo

`ValueDo` is now a class. Its `_type` (e.g. `scout.StringValue`) is set per instance and is available as constants (`ValueDo.STRING`, `ValueDo.LONG`, `ValueDo.DATE`, ...).
Create instances using the factory methods `ValueDo.ofString`, `ofLong`, `ofBoolean`, `ofDate`, `ofDateTime` or `ValueDo.of(typeName, value)` instead of object literals.

Value data objects are (de)serialized by the new `ValueDoSerializer`, e.g. the `value` of a `scout.DateValue` is converted to a `Date`.
Value types of your own project must be registered: `ValueDoSerializer.get().addTypeName('my.CustomValue', doValueMetaData.createSimple(String))`.
`ValueDoSerializer` always creates `ValueDo` instances, subclasses of `ValueDo` are not supported. If this is required, create a specific DO class subclassing `ValueDo` instead of registering it on `ValueDoSerializer`.

=== Empty @typeName Decorator No Longer Required

The build now collects the attribute data types required for the (de)serialization for all classes extending `BaseDoEntity` directly or indirectly.
Before, only classes having a `@typeName` decorator were considered.

Migration: remove empty `@typeName()` decorators, e.g. on abstract data object classes.
They are still required if the superclass differs from `BaseDoEntity` (which is not recommended!).

=== Removed and Renamed APIs

[cols="1,1"]
|===
|Old |New

|`AnyDoEntity` |`BaseDoEntity` (or `DoEntity` for plain objects)
|`CodeDo.text` |Removed. Use `texts`.
|`DataObjectDeserializer._TYPE_VERSION_ATTRIBUTE_NAME` |`dataObjects._TYPE_VERSION_ATTRIBUTE_NAME`
|`doValueMetaData.getArrayValueType` |`doValueMetaData.getFirstTypeArg`
|`doValueMetaData.getObjectTypeInfo()` result property `typeName` |`objectType`
|`DoValueMetaData.typeName` |`DoValueMetaData.objectType`
|===

New constants: `dataObjects._TYPE_ATTRIBUTE_NAME` and `dataObjects._CONTRIBUTIONS_ATTRIBUTE_NAME`.

New utility functions: `dataObjects.isEmpty`, `dataObjects.keys`, `dataObjects.values` and `dataObjects.entries`.
They ignore `_type`, `_typeVersion` and `_contributions`.
`objects.isEmpty` delegates to `dataObjects.isEmpty` for `BaseDoEntity` instances. A `BaseDoEntity` is therefore empty if all its properties except the ones mentioned above are `undefined`.

=== HybridManager Requires BaseDoEntity

The `data` parameter of `HybridManager.callAction`, `callActionAndWait`, `callActionAndWaitWithContext`, `openForm` and `createForm` is now of type `BaseDoEntity`.
The `data` of `HybridActionEvent` and `HybridActionEndEvent` and the result of `callActionAndWait` are `BaseDoEntity` instances as well.

Migration: replace object literals by data object classes with a `@typeName` matching the Java data object.

=== Unknown Data Objects

The following data is now deserialized without the `createPojoIfDoIsUnknown` option:

* data of hybrid actions and hybrid widget events (`HybridManagerAdapter`)
* `inputData` and `jsFormModel` of JS forms (`JsFormAdapter`)
* `jsPageModel` of JS pages (`OutlineAdapter`)

Objects whose `_type` cannot be resolved to a class and objects not having `_type` are now deserialized to plain `BaseDoEntity` instances instead of POJOs.

Migration:

* Declare a class with a matching `@typeName` for each data object you access.
* Use `dataObjects.stringify` instead of `JSON.stringify` and `dataObjects.parse` instead of `JSON.parse` where necessary.
* Do not compare such objects to object literals as `objects.equals` and `objects.equalsRecursive` consider objects with different prototypes as not equal.

=== Data Object Visitors

`dataObjectVisitors` now visits all properties of a `BaseDoEntity` except `_type`, `_typeVersion` and `_contributions`. Before, all properties starting with `_` were skipped.

=== Data Object Properties in ModelAdapter

A `ModelAdapter` can now declare properties containing data objects using `_addDataObjectProperties`.
These properties are deserialized when the model is initialized, on property change and model events, and serialized when sent to the server.
Replace manual calls to `dataObjects.deserialize` and `dataObjects.serialize` in your adapters by this declaration.

`ModelAdapter._remoteProperties` is now a `Set` instead of an array. `_addProperties` and `_removeProperties` only support `Set` containers now.

[#rest-resources-must-not-return-maps]
== REST Resources Must Not Return Maps

`AbstractRestResourceAnnotationTest` contains the new test `testMapReturnValue`, which fails for REST resource methods returning a `java.util.Map`.
Return a `DoMapEntity` instead. It can be created from a map using `DoMapEntity.of(map)` (keys must be converted to Strings first).

Override `acceptResourceForMapReturnValueCheck` or `acceptMethodForMapReturnValueCheck` to exclude resources or methods from the check.

== Karma Replaced by jasmine-browser-runner (Scout JS)

Karma has reached its end of life and has been replaced by https://github.com/jasmine/jasmine-browser-runner[jasmine-browser-runner].
At the same time Jasmine has been updated to version 7.
The commands `test-server:start`, `test-server:stop` and `test:ci` of `scout-scripts` (`@eclipse-scout/cli`) stay the same, only their configuration and arguments change.

=== Dependencies

* Remove the dependencies `karma`, `karma-*`, `@metahub/karma-jasmine-jquery` and `@eclipse-scout/karma-jasmine-scout` from your `package.json` files.
* Update `jasmine-core` to `7.0.2`, `@types/jasmine` to `7.0.0` and `jasmine-ajax` to `5.0.0`.
* Remove the `jasmine-core` override from your `pnpm-workspace.yaml` if you added it in a previous release.

=== Test Configuration

Rename the file `karma.conf.js` of each module to `test.config.js` and use the new base configuration `@eclipse-scout/cli/scripts/test-defaults`.
Static resources are no longer added using `config.files` and `config.proxies`, map the URL path to the directory in `config.resources` instead.

Before:

[source,js]
----
const baseConfig = require('@eclipse-scout/cli/scripts/karma-defaults');
const path = require('path');

module.exports = (config, specEntryPoint) => {
  baseConfig(config, specEntryPoint);

  const resDir = path.resolve('test/_res').replace(/\\/g, '/') + '/';
  config.files.push({pattern: resDir + '**/*.*', watched: false, included: false});
  config.proxies['/_res/'] = '/absolute' + resDir;
};
----

After:

[source,js]
----
const baseConfig = require('@eclipse-scout/cli/scripts/test-defaults');
const path = require('path');

module.exports = (config, specEntryPoint) => {
  baseConfig(config, specEntryPoint);

  config.resources['/_res/'] = path.resolve('test/_res');
};
----

Other Karma settings (e.g. `config.browsers`, `config.reporters`) have no equivalent, remove them.
See xref:technical-guide:user-interface/build-stack.adoc#test-configuration[Test Configuration] for the available properties and command line arguments (e.g. `--filter`, `--headless=false`, `--junitReportDir`).

The specs are executed in Chrome or another Chromium based browser (Chromium, Edge, Brave), which is started directly without a WebDriver.
If the browser is not installed at its default location, set the environment variable `CHROME_BIN` to the browser executable, as before with Karma.

=== Jasmine 7

Jasmine 6 and 7 contain breaking changes, see the release notes of https://github.com/jasmine/jasmine/blob/main/release_notes/6.0.0.md[Jasmine 6.0] and https://github.com/jasmine/jasmine/blob/main/release_notes/7.0.0.md[Jasmine 7.0].

== Updated Webpack Build (Scout JS)

The following dependencies have been removed from `@eclipse-scout/cli`: `copy-webpack-plugin`, `css-loader`, `mini-css-extract-plugin`, `terser-webpack-plugin`, `css-minimizer-webpack-plugin` and `fork-ts-checker-notifier-webpack-plugin`.
If your webpack configuration (e.g. `webpack.config.js`) uses one of them, migrate it as follows:

* `copy-webpack-plugin`: Use the `CopyPlugin` of webpack instead. It accepts the same patterns.
+
[source,js]
----
const {CopyPlugin} = require('webpack');
config.plugins.push(new CopyPlugin({patterns: [{from: 'res', to: '.'}]}));
----
+
Webpack refuses to copy files outside of `output.path` unless the target directory is allowed by `output.allowOutside`.
The default configuration of Scout already allows it for Maven modules.
* `mini-css-extract-plugin` and `css-loader`: Remove them from your rules and plugins.
Webpack processes CSS natively, so a rule only needs the preprocessor loader and `type: 'css'`.
The file name is configured by `output.cssFilename`, the options of `css-loader` are available under `module.parser.css` (see https://webpack.js.org/guides/native-css/#migration-guide[Native CSS migration guide]).
* `terser-webpack-plugin` and `css-minimizer-webpack-plugin`: Use `minimizer-webpack-plugin` instead and pass the options of the minimizer with the `minify` option:
+
[source,js]
----
const MinimizerPlugin = require('minimizer-webpack-plugin');
new MinimizerPlugin({
  minify: {
    implementation: MinimizerPlugin.esbuildMinify,
    options: {legalComments: 'none'}
  }
});
----
* `fork-ts-checker-notifier-webpack-plugin`: Removed without replacement.
If you still want desktop notifications, add the plugin to your own `package.json` and webpack configuration.

Furthermore:

* `less-loader` 13 reports Less warnings as webpack warnings by default.
To restore the previous behavior, set the option `lessLogAsWarnOrErr` of `less-loader` to `false`.
* After the build, files matching `*theme*.js` are no longer deleted from the output directory.
Webpack does not create JavaScript files for entries containing only Less or CSS anymore.

[[jquery-4]]
== jQuery 4 (Scout JS)

Scout JS now uses jQuery 4.1.0.
Update `jquery` to `4.1.0` and `@types/jquery` to `4.0.1` in your `package.json` files.

jQuery 4 contains breaking changes, see the https://jquery.com/upgrade-guide/4.0/[jQuery Core 4.0 Upgrade Guide].
The changes most likely to affect project code:

* Removed APIs: `$.isArray`, `$.isFunction`, `$.isNumeric`, `$.isWindow`, `$.type`, `$.trim`, `$.parseJSON`, `$.now`, `$.nodeName`, `$.camelCase`, `$.cssNumber`, `$.cssProps`, `$.unique` and `$.fx.interval`.
Use the native equivalents (e.g. `Array.isArray`, `typeof value === 'function'`, `String.prototype.trim`, `JSON.parse`, `Date.now`) or `objects.isFunction`, `objects.isArray` etc.
* `push`, `sort` and `splice` have been removed from jQuery objects. Use `[].push.call($elems, elem)`, `$elems.add(elem)` or collect the elements in an array first (e.g. `$($elems.toArray().sort(compareFn))`).
The `JQuery` interface of Scout no longer extends `Array`, so the TypeScript compiler reports calls of array methods on jQuery objects.
* `$.expr[':']` and `$.expr.filters` are deprecated. Use `$.expr.pseudos`.
* `.css()` only appends `px` to unitless numbers for a few properties (e.g. `width`, `height`, `top`, `left`, `margin`, `padding`). Specify the unit explicitly for all other properties, e.g. `$elem.css('font-size', size + 'px')`.
* `.attr(name, false)` removes the attribute for all non-ARIA attributes. Pass the string `'false'` to set the value `false` (e.g. `spellcheck`, `draggable`, `contenteditable`).
* `.outerWidth(true)` and `.outerHeight(true)` include negative margins.
* The focus events are fired in the order defined by the W3C specification: `blur`, `focusout`, `focus`, `focusin`.
* `.css('opacity')` returns an empty string for detached elements.
* `toggleClass(boolean)` has been removed.

The https://github.com/jquery/jquery-migrate[jQuery Migrate 4.x] plugin logs most of these usages to the console and can help to find them.

[[jquery-naming]]
== Renamed Properties Holding jQuery Objects (Scout JS)

Properties holding a jQuery object now consistently start with `$`:

* `FatalMessageOptions.entryPoint` has been renamed to `$entryPoint`.
* `BrowserField._externalWindowTextField` and `BrowserField._externalWindowButton` have been renamed to `_$externalWindowTextField` and `_$externalWindowButton`.

Adjust your code if you pass these options or access these properties in a subclass.

== jquery-scout: oneAnimationEnd Changed

`oneAnimationEnd` has been improved so the callback is now executed even when debugging or if the `animation-duration` is set to 0s.

This also comes with behavior changes:

. The function now must be called _after_ the animation has been started, e.g. after a class that starts the animation has been added.
If `oneAnimationEnd` is called before adding the animation class, the callback won't be executed anymore.
. Animations on pseudo-elements (`::before` and `::after`) are now ignored. If you need to react to animations on such elements, add a `nop` animation with the same duration on the actual element.

== jQuery Promises Replaced by Native Promises (Scout JS)

Scout JS no longer uses jQuery `Deferred`/`Promise`.
Every API that returned a `JQuery.Promise<T>` now returns a native `Promise<T>`, the Scout `Deferred` class is based on native promises, and `.done()`, `.fail()` and `.always()` are no longer available on the returned promises.
Project code that overrides or calls these APIs, including specs, has to be migrated.

=== Most Important Changes

* *Types*
** Replace `+JQuery.Promise<T>+` with `Promise<T>` and `+$.Deferred()+` with `+new Deferred<T>()+` of `@eclipse-scout/core`.
The TypeScript compiler reports almost all places that need a change.
* *Semantics*
** `.done()`, `.fail()` and `.always()` can't be replaced one-to-one by `.then()`, `.catch()` and `.finally()`.
All `.done()` handlers receive the original value, `.finally()` receives no value, a `.catch()` without rethrow resolves the chain, and native promises resolve and reject with exactly one value (e.g. `Promise.all()` and `$.when()` callbacks receive one array).
Review each of these places individually.
** `$.promiseAll()` is deprecated, use `Promise.all()` instead.
Its `asArray` parameter has been removed: it always resolves with an array, even for a single promise.
** `$.resolvedPromise()` and `$.rejectedPromise()` accept exactly one argument, multiple arguments are no longer supported.
** `$.resolvedDeferred()` is deprecated, use `$.resolvedPromise()` instead.
It also accepts exactly one argument.
** `$.ajaxJson()` is deprecated, use `ajax.getJson()` instead.
* *Timing*
** Native promises continue as microtasks, jQuery `.then()` handlers used `setTimeout`.
** `jasmine.clock().tick()` no longer drives promise chains: specs have to await the returned promise or an event (`+widget.when(...)+`) instead.
** Asynchronous work started while opening a form without awaiting its promise (e.g. a lookup in `Form.importData()`) is now overtaken the form itself and may lead to a wrong `saveNeeded` state. Try to return the promise, e.g. in `Form.importData()` which may now return a promise.
* *Errors*
** Unhandled rejections are no longer silently ignored.
A global handler passes them to the `ErrorHandler`, which logs them and shows the error message box.
You may want to catch them, throw an `AbortError` or consume them using `ErrorHandler.consume(error)`.
** Local `+.catch(error => errorHandler.handle(error))+` at the end of a promise chain are obsolete and can be removed.
** `ErrorHandler.handle()` does not accept multiple arguments anymore.
** SmartFields now check for `AbortError` instead of `error.abort`, so LookupCalls are now expected to throw an `AbortError` on abort.
** `ErrorHandler.handle()` ignores an `AbortError` (see `ErrorHandler.isIgnorableError()`), also for errors thrown in synchronous code.
Abort filters in front of `handle()` can be removed.
To skip the following `.then()` steps of an aborted chain, use `ErrorHandler.handleOrAbort()` instead: it rejects with an `AbortError`.
** An aborted `Call` (e.g. `AjaxCall`) now always rejects with an `AbortError`, also if the abort happens while a retry is scheduled or after the response has arrived.
Before, it rejected with an `AjaxError` with `+textStatus === 'abort'+` (or with the error of the last try) and resolved if the response arrived before the abort.
Replace checks for `+error.textStatus === 'abort'+` with `error instanceof AbortError`.
** Don't type the parameter of a `.catch()` handler as `AjaxError`: it receives every error of the chain (e.g. a `TypeError` thrown by a `.then()` step) and an `AbortError` if the call was aborted.
Check the type with `instanceof` instead.
** Errors in asynchronous code that runs after a widget has been destroyed are now visible, e.g. `+this.widget('MyField')+` returns `null` when a form has been closed while a request was running.
Call `this.throwAbortIfDestroyed()` before accessing the widget in such code: it throws an `AbortError` if the widget is destroyed or being destroyed.
** `ErrorHandler.formatAjaxStatus` and `formatAjaxRequest` have been replaced by `AjaxError.formatStatus` and `formatRequest`.
* *Forms*
** `Form.load()`, `save()`, `ok()` and `validate()` no longer show the error message box themselves, they only reject.
** `Form.close()` no longer returns a promise.

=== Recommended Approach: Migrate with an AI Agent

The migration consists of many small changes that are not purely mechanical.
We therefore recommend migrating with an AI coding agent like https://claude.com/claude-code[Claude Code] and reviewing the result.

Use the xref:promise-migration-guide.adoc[] as prompt for the agent.
It is written as instructions for an agent and contains the complete list of changed APIs, the translation rules and the pitfalls found in the migration of Scout and other projects.

After the migration review and test the changes thoroughly.

== Widget: Destroy Optimization (Scout JS)

The following changes have been made as part of a performance optimization.
However, these are actually internal methods, and it is very unlikely that your code uses them.

- `Widget._destroyChildren` and `Widget._destroyChild` have been removed without replacement.
- Widget.children is now readonly and can only be changed by the existing `Widget._addChild` and `Widget._removeChild_` methods.
